After `npm install <pkg>`, check `git diff package-lock.json`: npm 11 has dropped the `@rolldown/binding-*` optional dependencies from the lockfile here, after which vitest fails with "Cannot find native binding". Restore the lockfile and add only the new package's entries. Stop `npm run dev` before `npm ci`: on Windows the dev server holds lightningcss's `.node` file, and `npm ci` deletes most of `node_modules` before failing with EPERM.

## Next.js 16.4 specifics

- This Next version differs from training data. Read the bundled guides in `node_modules/next/dist/docs/` before writing Next code (see `AGENTS.md`).
- `cacheComponents` and `partialPrefetching` are on. Request-time reads (Supabase, `searchParams`, `headers()`, current time) must sit inside `<Suspense>`. In the `npm run build` route table, pages with live data should show ◐, not ○.

## Architecture

- **Users and sessions.** Supabase Auth with email and password (`/masuk`, `/daftar`, actions in `src/app/masuk/actions.ts`). Self-hosted Supabase has no SMTP, so it runs with `ENABLE_EMAIL_AUTOCONFIRM=true`: no confirmation mail, no password reset. `src/lib/auth.ts` builds the cookie-based client from `@supabase/ssr` (auth only, never data) and exposes `currentUser()` and `requireUser()`, which read the session with `getClaims()`; `getSession()` would trust the cookie unverified. `src/proxy.ts` refreshes the session on every request and sends visitors without one to `/masuk?next=…`; only `PUBLIC_PATHS` there (`/masuk`, `/daftar`, `/privasi` for the Meta app) and `WEBHOOKS` (Meta's and Mayar's) skip it. New public endpoints go in that set. Every page loader, route handler and server action still calls `requireUser()` itself, outside any `try`, because its `redirect()` throws. Session cookies belong to one host, and the OAuth callbacks read the session, so `APP_URL` and the dashboard must be on the same domain as the callbacks: in dev, open the ngrok domain, not localhost. The Meta app's OAuth redirect URI is that domain with a trailing slash (`INSTAGRAM_REDIRECT_URI=https://<domain>/`; the token exchange fails without the slash), so `src/proxy.ts` rewrites `/?code=…` and `/?error=…` to the callback route and `next.config.ts` skips its `/` redirect for them.
- **Server-only code.** Modules in `src/lib` that touch secrets `import 'server-only'`. Vitest aliases that import to a stub (`vitest.config.mts`).
- **Data access and tenancy.** `db()` in `src/lib/supabase.ts` is the service-role client. Tables have RLS on with no policies, so the publishable key can read nothing; that stays, because RLS policies would let users write their own rows directly and skip the post lock and the AI limit. Isolation lives in `src/lib`: every data function takes `userId` first and filters with `.eq('user_id', userId)` (or passes `p_user_id` to an SQL function), and every table carries `user_id` referencing `auth.users` with `on delete cascade`. Former singletons (`instagram_connections`, `facebook_connections`, `brand_kit`, `dm_settings`) are keyed by `user_id`. DM keys are `(user_id, igsid)` and `(user_id, mid)`, because two users of the app messaging each other see the same `mid`. `save_post` refuses another user's photos. A `before delete` trigger on `auth.users` removes the user's posts first, since `post_media` restricts deleting a photo in use. Rows from before multi-user belong to the first auth user (`20261016040000_multi_user.sql`). New Storage objects go under `<userId>/`. Schema changes go in new files under `supabase/migrations/`.
- **Akun Instagram.** One Instagram account is one brand. The dashboard tables (`brand_kit`, `brand_references`, `assets`, `posts`, `content_ideas`, `dm_*`) carry `account_id` (the connection's `instagram_user_id`); a `before insert` trigger (`stamp_account()`) stamps the account connected at that moment, so inserts and SQL functions never pass it, while dashboard reads filter by the `accountId` that `requireAccount()` (`src/lib/auth.ts`) returns. `account_id` is a display filter, not a security boundary: per-id actions still filter by `user_id` only, except what goes out to Instagram: `save_post` raises `wrong_account` when scheduling a post of another account, `retryPost` filters by account, replies need the account-filtered `getConversation`, and the worker fails a post whose `account_id` isn't the connection's ("Akun Instagram berbeda", no retry, container kept). AI prompts read the connected account's brand inside `brand.ts` (`loadConnectedKit`), so AI functions take only the user. `requireAccount()` gates Brand, Buat, Kalender, Aset and Balasan (pages, actions) and sends a user without Instagram to `/pengaturan?perlu=instagram`; Pengaturan, Langganan and the OAuth routes keep `requireActiveUser()`. Putuskan (`disconnect_instagram()`) turns the account's scheduled posts into drafts and deletes the connection in one transaction; nothing else is deleted. The Instagram callback reads the previous account before saving, drafts its scheduled posts when another account logged in, hands rows without an account to the new one (`claim_orphan_rows()`), and, when the account has no `brand_kit` row yet, claims one with `sync_status = 'running'` and runs `syncNewAccount()` (`src/lib/brand-sync.ts`) in `after()`: profile text, profile picture as logo, the 3 newest photo or carousel posts as references, colours from their covers (`paletteFromBytes`, sharp), visual style; its AI requests are logged at 0 credits (`{ cost: 0 }`, only there). Singletons (`brand_kit`, `dm_settings`) are unique on `(user_id, account_id)` and upsert with that `onConflict`; `facebook_connections` is keyed by user and `instagram_user_id`. The profile picture URL is signed: never pass it into logged AI sources.
- **Instagram connection.** Lives in `src/lib/connection.ts`: one `instagram_connections` row per user, with `instagram_user_id` unique, so an account connected by another user fails with `AccountTakenError` (`?ig_error=akun_dipakai`). One-time `oauth_states` record the user who started the login, and the callbacks redeem a state only for that same signed-in user, so a login link someone else started can't attach their account to yours. Raw HTTP to Instagram is in `src/lib/instagram.ts`. Anything that calls Instagram gets its token from `getValidAccessToken()`, which decrypts it, refreshes it lazily (when older than 24 hours and within 7 days of expiry), and flips status to `needs_reconnect` on Graph error 190.
- **Tokens.** Encrypted with AES-256-GCM using `TOKEN_ENCRYPTION_KEY`. Changing the key makes stored tokens unreadable, so the owner must reconnect.
- **Logging.** Graph API GETs carry `access_token` in the query string. Never log URLs or raw fetch errors; log through `describeError()`.
- **OAuth errors.** They reach the browser only as `?ig_error=<code>`, mapped to Indonesian messages in `src/app/(app)/pengaturan/instagram-settings.tsx`.
- **Posts.** Tables `assets`, `posts`, `post_media`, `publish_attempts`; data access in `src/lib/posts.ts` and `src/lib/assets.ts`. Post content changes only through the `save_post()` SQL function, which swaps caption, schedule and photos in one transaction and raises `post_locked` for posts the worker owns. Status-only changes (cancel, retry, delete) are conditional updates that report whether they won.
- **No duplicate posts.** A non-null `posts.ig_container_id` means Instagram may already have published the post, so its content stays locked. The worker saves the container id before `media_publish`, checks the container's `status_code` before any retry (`PUBLISHED` means done), and clears the id only when it is certain the post did not go out.
- **Worker.** `src/worker/` runs apart from Next via `tsx` with `--conditions=react-server`, which makes `server-only` resolve to an empty module. It polls `claim_due_post()` (`FOR UPDATE SKIP LOCKED`; a post stuck in `publishing` for 10 minutes is reclaimed) and retries transient errors after 1/5/15/30 minutes, at most 5 attempts. The same process runs two slide loops beside it, polling `claim_next_slide()` every 3 s (`SKIP LOCKED`; a slide stuck in `generating` for 5 minutes is reclaimed). In production it runs on the VPS next to Supabase under pm2 or systemd.
- **Media and Aset.** Photos are cropped to 4:5–1.91:1, capped at 1440 px and re-encoded as JPEG in the browser (`toInstagramJpeg`) before upload; website images use the matching server-side conversion in `src/lib/slide-image.ts`. `assets` carries `origin` (`upload`, `website`, `ai`), optional `asset_groups`, per-photo `is_active`, source URL and content hash. `/aset` separates Milik saya from Hasil AI, each loaded apart (newest 100 each, `listAssetLibrary`) so slides can't push the owner's photos out. Milik saya has a Produk card (filter, add, edit, delete groups; `photoCount` counts the loaded photos), a Dari website card that imports from the website saved in Brand, an upload zone that can file photos straight into a product (`uploadAsset` with `groupId`) and tag them with AI, and a grid with checkboxes, a bulk bar (move, activate, pause, AI tags, delete; actions take repeated `id` fields, at most 100) and an Ubah panel per photo. Hasil AI photos can only be deleted. Photos carry `tags` (lowercase, distinct, ≤20 of ≤40 characters, `src/lib/asset-options.ts`); `tagAssets()` (`src/lib/asset-ai.ts`) tags own photos in visual batches as `asset_tags`, charged per photo (`tagCost`), and a batch whose answer misses a photo is charged nothing; the website catalog asks for tags in the same request at no extra cost. Nothing reads tags for content yet. Paused photos still appear in the manual picker but AI ignores them, and AI results (`origin = 'ai'`) are never sent as product photos. The `media` bucket is private; Meta gets signed URLs built from `NEXT_PUBLIC_SUPABASE_URL`, so that must be the public HTTPS domain, not an internal address. Signed URLs carry a token: never log them.
- **DMs.** Meta posts DMs to `src/app/api/webhooks/instagram/route.ts`. The GET handler answers the verify handshake (`INSTAGRAM_WEBHOOK_VERIFY_TOKEN`). The POST handler hashes the raw body and checks `X-Hub-Signature-256` against `INSTAGRAM_APP_SECRET` before parsing it (`src/lib/dm-webhook.ts`). It hands each `entry.id` to the user who connected that account (`findUserByInstagramId`) and drops the rest, and it answers 5xx only when storing fails, because Meta retries those. Opening the DM tab and Muat ulang also pull DMs from Instagram (`syncConversations()`, `src/lib/inbox-sync.ts`): the 100 newest conversations of `/me/conversations` with their 20 newest messages (Instagram details no more), at most every 10 minutes (`instagram_connections.dms_synced_at`, cleared on failure and on connecting), so chats from before the account was connected, or from while the webhook was off, show too; the API's message ids are the webhook's `mid`, and only those not stored yet are recorded (`listStoredMids`). Every message goes through `record_dm_message()`, keyed on Meta's `mid`. That makes retries and the echo of the app's own sends no-ops, and a late webhook never moves a conversation's summary or its 24-hour window. Replies go out from a server action (`sendDirectMessage`, Bearer token, JSON body), and only within 24 hours of the customer's last message. Meta delivers webhooks only once the app is Live; `ensureWebhookSubscription()` automatically subscribes each saved token through `/me/subscribed_apps` with `messages,messaging_postbacks,comments` after OAuth (without `comments` while the connection lacks `COMMENTS_SCOPE`: Meta refuses the whole call for a field without its permission), and the notification poll also backfills older connections with a one-hour retry cooldown. `/balasan` (`src/app/(app)/(halaman)/balasan/`) has tabs `?tab=komentar`, a filter (`?filter=semua`; Belum dibales by default) and one list whose thread opens under its row (`?c=<igsid>`, the link of the open row closes it). A conversation is unread when the customer wrote last after `seen_at` (`isConversationUnread`, `src/lib/inbox-rules.ts`); opening a thread calls `markConversationSeenAction` from the browser (never a write during render, and no `refresh()`). The webhook reads the customer's name, username and `profile_pic`; opening the inbox also fills up to 12 missing/stale profiles, so old conversations gain profiles too. Profiles older than 3 days are read again (`profile_fetched_at`) because the picture is a signed CDN link shown with an initials fallback (`ProfileAvatar`): never log it. The reply box (`composer.tsx`) is controlled state sent through the action directly, with template chips (✎ opens Template balasan through a window event, `templates-events.ts`), an emoji popover and ✨ AI. ✨ AI is `draftReply()` (`src/lib/reply-ai.ts`, task `reply_draft`, 1 credit): an empty box gets a draft from the last 10 messages, a filled one is tidied; it answers `{"reply": "…"}`, cut to the channel's limit, and only ever fills the draft. Helpers that aren't actions live in `balasan/action-utils.ts`, because everything exported from a `'use server'` file is a public action. Template matching and filling are pure functions in `src/lib/dm-templates.ts`: a keyword must appear as a whole word, case-sensitive, as the owner chose. Templates only ever fill the editable draft.
- **Auto DM.** Rules in `auto_dm_rules` (`src/lib/auto-dm.ts`; shape, validation, matching and the DMs they send are pure in `src/lib/auto-dm-rules.ts`, shared with the form) answer automatically, unlike templates: saving an active rule is the owner's approval. The form is `/balasan/auto-dm` (`?id=` to edit; `auto-dm/`), the rule cards with Jedakan/Ubah/Hapus and the last run sit under the DM list (`auto-dm-rules.tsx`, actions in `auto-dm-actions.ts`), and `?filter=otomatis` lists conversations a run talked in. The Instagram webhook hands what it stored for the first time (customer DMs, postback taps, comments) to `runAutoDm()` (`src/lib/auto-dm-runner.ts`) in `after()`, so Meta isn't kept waiting: one active rule per trigger (`pickRule`: one post's rule before every post's, keywords before any comment, then oldest), claimed through `claim_auto_dm_run()` (one run per comment or `mid`, and one per rule and person in 24 hours), then the optional public reply (`replyToComment`, random variation) and the first DM as a private reply, or to the IGSID for a DM trigger (`sendAutoDm`, a button template when it has buttons, 640 characters). A tap on a button (`autodm:<ruleId>` postback, stored as the customer's message, which dedupes on its `mid` and opens the 24-hour window) gets the follow request or the main message: with the follow gate on, `fetchFollowsBusiness` decides, and a failed check sends nothing. Every outcome lands on the run (`step`, `error`), which the card shows; only the webhook triggers rules, never a pull, and paused rules ignore taps too.
- **Komentar.** Comments of the account's posts live in `ig_comments` (`src/lib/comments.ts`), keyed `(user_id, comment_id)`. They arrive two ways: the `comments` webhook (`parseCommentEvents`, `entry.changes[]` or `field`/`value` on the entry, stored insert-only so a retry changes nothing) and a pull (`syncComments()`, `src/lib/comment-sync.ts`) of posts from the last 30 days (`COMMENT_DAYS`), run when the Komentar tab opens and from Muat ulang, at most every 10 minutes (`claim_comment_sync()`), 3 posts at a time; a complete listing removes comments Instagram no longer has. It needs `instagram_business_manage_comments` (`COMMENTS_SCOPE`); older connections get a Hubungkan ulang notice. The account's own comments (`isOwnComment`: its id, else its username) are stored as replies, never counted as waiting or new, and `mark_comment_replies()` sets `replied_at` on the comments they answer. The tab lists posts (`?tab=komentar&post=<media-id>` opens one, which marks its comments seen) with each comment's replies; actions in `comment-actions.ts`: public reply (≤2,200 characters, `COMMENT_MAX_LENGTH`), hide/show, delete (`window.confirm`), and one private reply per comment within 7 days (`canPrivateReply`, `sendPrivateReply` with `recipient.comment_id`; `dm_sent_at` records it). ✨ AI there reads the comment thread and the post's caption.
- **Notifikasi.** The bell in the app header (`src/components/notification-bell.tsx`) counts unread DM conversations plus new comments that wait for a reply (`summarizeNotifications`, pure, in `inbox-rules.ts`; no notification table, all from `seen_at`) and lists the newest 10. It polls `GET /api/notifikasi` (`getNotificationFeed()`, `src/lib/notifications.ts`) every 10 s while the tab is visible, when the tab is shown again and after each page change; a route handler rather than a server action, because a page runs its actions one at a time and a long AI request would hold the poll. Without a connected account or a current period the feed is disabled and the bell hidden. Tandai semua dibaca is a server action (`markAllSeenAction`).
- **Time.** Schedules are entered and shown in WIB (fixed +07:00, `src/lib/format.ts`); the database stores UTC.
- **AI.** `src/lib/nine-router.ts` is the raw HTTP client. `src/lib/ai.ts` holds what every task shares: `runLogged()` wraps every 9Router call, checks the period's credits first, logs the request to `ai_generations` and charges `TASK_CREDITS[task]` (`src/lib/billing-options.ts`) or the `cost` it is given against the plan's credits (`getPlan()`), counted with `credits_used()` from that table minus `credit_adjustments`; the guide is `docs/kredit-ai.md`; failed requests cost 0. Writes that make a result usable (a new post, ideas) run inside its `ask`, so when they fail the owner isn't charged. A credit count that can't be read blocks AI rather than reading as 0. Requests must send `stream: false`, or 9Router answers with SSE. A 200 can carry a provider notice instead of an answer, so only JSON the task's parser accepts counts as success (`readJson`, else `AiOutputError`). Prompts quote owner text between `"""` and add the brand kit's text (`loadBrandContext()`, `describeBrand()`); brand facts count as facts the model may use, and a brand kit that fails to load leaves the content unbranded instead of failing it. Text tasks are in `src/lib/content-ai.ts`, brand tasks in `src/lib/brand-ai.ts`.
- **Buat Konten.** `/buat` (`src/app/(app)/buat/`, actions in `content-actions.ts`) is a content list and an editor with one composer. A topic becomes a draft with a title, caption and 1–10 waiting slides, charged once with `contentCost(slides)` (`create_content()` stores it inside that request). The composer offers Product Otomatis/Tanpa/one active product group; the planner chooses `product_group_id` per slide, and that choice stays on retries and edits. A carousel's prompt carries `carouselGuide()` (`src/lib/carousel-guide.ts`), anti-generic copy rules distilled from the owner's carousel knowledge base, with one hook archetype picked at random per post; the model checks the rules itself in the same request, because a reject-and-retry loop would charge 9Router again. The worker then makes the slides (`src/lib/slide-generation.ts`), one at a time per post in carousel order, so closing the tab doesn't stop them (`claim_next_slide()`, image, `toSlideJpeg`, Aset, `attach_slide()`); the editor only refreshes until they land. They cost nothing (`content_slide`); a timeout, 429 or 5xx from 9Router is retried after 30 s and 2 min (`requeue_slide()`, at most 3 tries), anything else fails, and Coba lagi (`retry_slide()`) puts a failed one back in the queue. Edits go through the composer: a slide is revised from its stored prompt and redrawn from its current image (`replace_slide()`, `slide_edit`), a caption is rewritten (`caption_edit`, with Urungkan). The composer types like an editor (Enter is a new line, Ctrl/⌘+Enter sends) and takes one image, picked or pasted (`src/lib/attachments.ts`, re-encoded to a 640 px JPEG on the server): an edit sends it to `reviseSlide` and the image model with the instruction as its note, unstored; for a new post the planner sees it and writes per slide what to do with it (`attachment`, empty when unused; without the owner's say it decides from the image: a finished design is a layout reference, a photo is shown; all empty sends it to every slide with a note that lets the image model decide), and it is stored at `brand/<userId>/lampiran/<uuid>.jpg` for those slides (`post_slides.attachment_path`, `attachment_note`), so a retry still has it. The composer has no reference choice: new posts follow the account's references, or the style's examples without any, and a specific design or footage comes as an attachment. Photos are added to a post from the mockup's Tambah foto card after the last slide or the strip's + tile. Slide text is up to 300 characters, cut after the last sentence that fits, never inside a word. The editor autosaves caption and photo order through `save_post()` a second after typing; that and Jadwalkan are refused while slides are pending or generating, because `save_post` replaces the photo list and would drop an image that lands meanwhile. Server actions run one at a time per client, so the caption is read-only while an AI request runs. Slide prompts and the queue live in `post_slides` (`src/lib/slides.ts`), apart from `post_media`, which stays what the worker publishes. Ideas come from the brand kit (`content_ideas`, `src/lib/ideas.ts`). An idea opened without a script gets one at once (`content_script`, 3 credits, `writeScript`; Susun ulang writes it again): the AI picks 2–10 slides and writes each one's label, title and body (`src/lib/script-options.ts`), stored on the idea (`content_ideas.script`). The script is the composer's text, not a panel: each slide is a `Slide N — label` line, the title (the next line with text), then the body, a blank line apart (`scriptToText`, `readScriptText`). The composer draws it formatted under a transparent textarea (`format`, `formatScript` in `script-text.tsx`): slide lines in the accent, red while that slide can't be made, titles stroked bold; only color and stroke, because the copy must wrap exactly like the textarea. While the text reads as a valid script it is autosaved on the idea; text without slide lines is a plain topic. The browser sends the script with `createContentAction`, which checks it with `parseScript`: the slide count is the script's, the planner writes only caption and scenes (the idea and any text above Slide 1 are the topic), and each headline is replaced with the script's text after parsing. `?tanggal=` from Kalender suggests that day at 19.00 (`slotOn`).
- **Langganan.** Payments are off unless `MAYAR_ENABLED=true` (`paymentsEnabled()`): while testing, sign-up grants a free period (`grantFreePeriod`, an amount-0 row through the same `activate_payment`) and the button on `/langganan` grants another, so credits and expiry still behave as with paid periods. A subscription is not a table: a user is active while a `paid` row in `payments` covers now (`getCurrentPeriod`, `src/lib/billing.ts`), and `activate_payment()` starts the next period at the end of the last one, so paying early stacks. `requireActiveUser()` (`src/lib/auth.ts`) gates every `(app)` page, its actions and the OAuth routes; `/langganan` itself only needs a session. Checkout is a Mayar Single Payment Request (`src/lib/mayar.ts`): the `payments` row is written before Mayar is asked, and an open link is handed out again instead of creating another. Mayar signs no webhooks, so `/api/webhooks/mayar` only names payments, and a payment counts as paid only when Mayar's API answers `paid` for the same amount to our key (`confirmPayment`). Opening `/langganan` checks pending payments too, so a lost webhook only delays activation. The worker fails posts of users whose period ended, keeping any container. The owner's free period (to 2099) is a `payments` row with amount 0; other free accounts get the same row by hand. The webhook's id field (`webhookPaymentIds`) is a guess (`productId`, then `id`) until checked against Mayar's webhook history in sandbox.
- **Admin.** `/admin` (`src/app/(app)/(halaman)/admin/`, actions in `actions.ts`, data in `src/lib/admin.ts`) is for the emails in `ADMIN_EMAILS`. `src/proxy.ts` rewrites `/admin*` for any other signed-in user to a route that doesn't exist, so they get a real 404 status (`requireAdmin()` runs inside Suspense, after the 200 is sent, and stays as the check for the pages and actions). Admin needs no subscription, and neither does the sidebar (`requireUser()`, not `requireActiveUser()`), so an admin without one isn't sent to `/langganan`; an admin can't end their own subscription. Admins override the text and image model and the plan in `app_settings` (one row; empty columns fall back to `ROUTER_MODEL`, `ROUTER_IMAGE_MODEL` and `DEFAULT_PLAN`). Read them only through `src/lib/app-settings.ts` (`textModel()`, `imageModel()`, `getPlan()`), which caches the row 30 s per process and uses the defaults when it can't be read; `chatCompletion` and `generateImage` take an optional model for the admin's live test. Per user an admin grants free days (`grantFreePeriod(userId, days)`), ends the subscription (`admin_end_subscription()`: the current period ends now, periods paid ahead become `expired`), gives or takes credits (`credit_adjustments`, positive gives back, only with a current period; reset = give back what was used), sets a password (no SMTP, so this is the reset), bans through Supabase Auth, and deletes the user (typed email, never oneself; Storage files under `<userId>/` are removed afterwards, best effort). Every action lands in `admin_log`. User detail is `/admin/pengguna?id=`, not a `[id]` segment: a dynamic segment makes `usePathname()` in the layout fail the build under Cache Components.
- **Analitik.** `/analitik` (`src/app/(app)/(halaman)/analitik/`) shows the connected account's posts of the last 90 days (`?rentang=7|30|90`) from `ig_media`, one row per post with the latest lifetime insights (views, reach, likes, comments, shares, saved, total_interactions; null is shown as "—", not 0), and marks those the worker published (`posts.ig_media_id`). It needs `instagram_business_manage_insights` (`INSIGHTS_SCOPE`, read from `instagram_connections.scopes`); accounts connected before it get a Hubungkan ulang notice. `syncAnalytics()` (`src/lib/analytics-sync.ts`) runs from the Refresh action and once on page open when the last sync started over 6 hours ago; `claim_analytics_sync()` gives a 10-minute cooldown and one sync at a time, and a failed sync clears its claim. It lists `/me/media` by cursor (`listMediaSince`, at most `MAX_SYNC_POSTS`; pinned posts may be older), reads insights 3 at a time, retries transient errors twice, stops asking after a rate limit, and aborts only on a rejected token. A post whose insights fail keeps all its old numbers, likes and comments included (it is upserted without the metric columns), with `insights_error`. A complete listing deletes the account's rows it no longer has. Pure parsing and math are in `src/lib/analytics-metrics.ts`. Thumbnails are signed CDN links: never log them.
- **Brand kit.** Tables `brand_kit` (one per user and account), `brand_references` with `brand_reference_images`, and `facebook_connections` (one per user and account); a reference is a group: one photo (`single`) or every slide of a carousel, labelled `cover`, `isi` or `cta` by position, a one-image reference `single`, shown as Umum (`labelsForCount`; the owner can change every label, a one-image reference's too) and shown as a slideshow. Buat Konten picks each slide's reference image when the post is made (`planReferenceImages`, stored in `post_slides.reference_image_id` with the slide's `role`): one cover, one inner and one CTA image, at random from all of the account's groups (Otomatis; the composer no longer offers Tanpa or one group, which `chooseSlideReferences` still takes). A role without an image of its own label takes one Umum image, the same for every such role, else none, never the cover's; an Umum image gives its layout only to a cover or a one-image post, other slides take just its style. An account without references follows its design style's example slides instead (`planStyleExamples`: one set per post, keys in `DESIGN_STYLES[...].examples`, files in `assets/contoh-desain/`, chosen keys in `post_slides.example`). Instagram media are read with `children` (`MEDIA_FIELDS`); videos are skipped, and Business Discovery asks `children{media_type,media_url}` without `thumbnail_url`. data access in `src/lib/brand.ts`, shared fields and validation in `src/lib/brand-options.ts`, prompts in `src/lib/brand-ai.ts`. Images live in the private `brand` bucket (JPEG, PNG, WebP), apart from `media`, so other accounts' photos never reach the post picker. Profile and visual-style analysis only fill the form; the owner saves. Palettes are computed in the browser from pixels (`src/lib/palette.ts`); the fetch uses `cache: 'no-store'` because Storage sends no `Vary: Origin` and the card's `<img>` would otherwise leave a cached copy without CORS headers. Anything fetched from outside goes through `fetchPublic()` (`src/lib/web-fetch.ts`), which checks hostname and resolved addresses at every redirect, refuses loopback/private destinations, and caps time and bytes. Website reading runs no JavaScript: regex over bounded HTML/CSS (`src/lib/website.ts`) crawls the homepage plus at most 10 same-host pages, prioritizes product paths, and exposes up to 40 useful raster candidates. `src/lib/website-import.ts` converts them to JPEG and dedupes by normalized source URL and content hash; `src/lib/website-ai.ts` groups them in visual batches logged as `website_catalog` without logging image data or source URLs.
- **Business Discovery.** Reading other accounts needs Facebook Login (`src/lib/facebook.ts`, routes under `src/app/api/auth/facebook/`, the callback in `PUBLIC_PATHS`), separate from Instagram Login. The callback keeps a Page token derived from a long-lived user token, which does not expire. It picks the Page whose Instagram account is the connected one. `FACEBOOK_LOGIN_CONFIG_ID` switches the dialog from `scope` to Facebook Login for Business. The username is interpolated into Graph field syntax, so `parseInstagramUsername()` must keep it to `[a-z0-9._]`.
- **Gambar AI.** `drawImage()` in `src/lib/image-ai.ts` makes one image and is wrapped in `runLogged` by its caller; shared choices are in `src/lib/image-options.ts` (4:5 and 1:1 only). Every prompt carries `LAYOUT_RULES` (text and imagery in full-width horizontal bands, never a text column beside a photo; nothing cut off at the edges; how a photo meets the text is left to the reference or example, since a fade rule there overrode their hard edges) and tells the model to keep every word of the text; inner slides are text-led. All text that appears in an image belongs in the slide's headline: the prompt quotes it exactly, and without one it forbids any text, because the model otherwise adds words of its own. `generateImage()` asks 9Router for SSE (`progress` events keep the connection open through nginx; `done` carries `b64_json`, `error` a message) and JPEG. Input images (the slide being edited, the owner's attachment, up to two active non-AI photos of its selected product, the slide's design reference or style example, the post's first inner slide only for an inner slide with neither, the logo, in that priority; the cover is never sent to another slide) go as data URLs in `images[]` and are packed into `VISUAL_BODY_BUDGET`; 9Router forwards URLs to OpenAI, which needs HTTPS. Stored slides go back as 640 px JPEGs (`toReferenceDataUrl`). The provider's image is cropped to the format's exact size on the server with sharp (`src/lib/slide-image.ts`, the server's `toInstagramJpeg`), which must stay inside its `try`: sharp throws synchronously for empty bytes. Logs keep the prompt and the byte count, never image data.

## Rules carried from the PRD

- AI output and reply templates are always an editable draft. Nothing publishes or sends a DM without an explicit owner action, except an active Auto DM rule, which the owner chose on 2026-10-19 to let answer comments and DMs on its own; it only ever answers someone who commented or wrote first. No bulk or unsolicited DMs. No scraping outside Sigap's explicit Intel Kompetitor exception: only when the owner turns on the Intel Kompetitor toggle (`deepSearch` in code), `src/lib/apify.ts` may call Apify's `apify/instagram-scraper` for public Instagram profiles and recent public posts; cap it at `DAILY_LIMITS.deep_search`, never persist or log signed avatar URLs, and do not reuse it elsewhere.
- Scheduled publishing and AI slide generation run in the worker process (`npm run worker`), never in the browser or the Next server.
- Meta cannot fetch `localhost` media. Publish from Supabase Storage URLs.
- 9Router is called only from server code. Images come from `ROUTER_IMAGE_MODEL` (default `cx/gpt-image-2.5`, working after the owner updated 9Router on 2026-10-16; before that the Codex provider refused every image model). `/v1/models` does not list image models; the 9Router dashboard does. The PRD names the `Hermes-daily` combo, but on 2026-10-16 it answered every request with "Gemini 3.5 Flash is no longer available…", so `ROUTER_MODEL` is `cc/claude-haiku-4-5-20251001`. Verify a new `ROUTER_MODEL` with a live request; the tests mock 9Router. Vision works with `image_url` data URLs (2026-10-16). Request bodies pass an nginx with the default 1 MB `client_max_body_size` (HTTP 413 above it), so visual analysis packs references into `VISUAL_BODY_BUDGET`. Image URLs need HTTPS, which the Storage URL isn't yet. After a provider error 9Router may answer the next requests with the same error and "reset after 30s".
- `INSTAGRAM_ACCESS_TOKEN` in `.env.local` is a manual test token. The app does not use it.
